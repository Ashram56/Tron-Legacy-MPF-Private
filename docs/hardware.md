# Hardware configs: the P-ROC machine and the virtual one for MPF Monitor

Decision (Vincent, 2026-10-03): a Multimorphic **P-ROC** takes the place of the SAM CPU board. It drives
the original Stern SAM IO (driver and lamp) board. In MPF terms that is platform `p_roc` with
`driverboards: sternSAM`.

The machine config `game/config/config.yaml` is platform neutral. It has no `hardware:` section, and its
numbers are the LE ROM's SAM numbers. A hardware overlay is picked at launch, for a Pro (the default) or an LE
(see "Pro or LE" below):

| Launch (in `game/`) | Overlay | For |
|---|---|---|
| `mpf game . -c config,hw_virtual` | `hw_virtual.yaml` (Pro), `hw_virtual_le.yaml` (LE) | The desktop and MPF Monitor. Uses smart_virtual. The trough starts full, eject coils move balls between the trough, shooter lane and VUK, and the trough switches shift like the real trough (`tron/virtual_hardware.py`). |
| `mpf game . -c config,hw_proc` | `hw_proc.yaml` (Pro), `hw_proc_le.yaml` (LE) | The real machine, with the P-ROC on the SAM IO board. |
| `mpf game . -c config,hw_vpx` | `hw_vpx.yaml` (LE), `hw_vpx_pro.yaml` (Pro) | Visual Pinball X ([vpx.md](vpx.md)). The VPW table is an LE, so the plain overlay is the LE here. |

## Pro or LE

Decision (Vincent, 2026-10-04): the game runs on either model, **default Pro**. The LE 1.74 ROM has no Pro
mode; the Pro 1.74 ROM is a separate image with different IO assignments. `assets/docs/PRO_VS_LE.md` and
`assets/io/pro_vs_le_io_map.csv` list them:

| | LE | Pro |
|---|---|---|
| Switches 1-4 | T-R-O-N drop targets, sw 1 = T | T-R-O-N standups, reversed: sw 1 = N |
| Switches 54-56 | Recognizer motor positions | none |
| Coil 3 | drop target reset | disc direction relay (22 on the LE) |
| Coils 19, 25 | left, right ramp flash | the ramp flashers (the Pro ROM names them back center, back left) |
| Coils 22, 23 | disc direction relay, Recognizer motor relay | flashers lower left, lower right: fired with 19 / 25 |
| Coils 31, 32 | red disc, blue disc flash | red disc left, right (same outputs: the rules drive them on both) |
| Lamps 1-66 | LE matrix | renumbered; no Recognizer position lamps |
| Ramp light tubes (fiber optics, aux bus) | fitted | not fitted; off unless enabled |

How it is built:
- `config.yaml` keeps the LE numbers: the rules, the shows and the ROM traces all use them. The rules find a
  device's ROM number by name (`tron/hw_numbers.py`), so they light the right lamp on either machine.
- `machine_pro.yaml` includes `rom/pro_numbers.yaml` (generated by `scripts/gen_config.py` from the map): the Pro
  number of every device that moves, the Pro's own flashers, and `platform: virtual` for the LE devices the Pro
  does not have (drop target reset, Recognizer motor relay and position switches and lamps). They
  stay defined because the rules still address them. On the Pro the TRON standups go through the ROM's
  drop-target code with nothing to reset: a hit target counts once until all four are hit.
- `machine_le.yaml` and `machine_pro.yaml` set the machine vars `machine_variant` (`le` / `pro`) and `fiber_optics`.
- The Pro overlays are the LE ones plus `machine_pro.yaml`; `hw_proc.yaml` adds `rom/proc_numbers_pro.yaml`, the
  P-ROC numbers for the Pro.
- **Fiber optics**: the Pro has no ramp light tubes, but its IO board has the aux bus driver and nothing else is
  wired to those outputs, so the tubes stay defined. They are driven only when `fiber_optics` is 1: always on an
  LE; on a Pro add `fiber_optics` (`mpf game . -c config,hw_proc,fiber_optics`, `run.py --fiber-optics`,
  docker `TRON_FIBER_OPTICS=1`). On the P-ROC they also need `proc_ramp_tubes` (below).
- `scripts/run.py --machine pro|le` picks the overlay (docker: `TRON_MACHINE`). `--scenario` defaults to the LE,
  since the traces are the LE ROM's.
- The rules are the LE's on both machines (End of Line multiball included; [rom_differences.md](rom_differences.md)).
  The Pro decompile (`assets/rom_data/pro/`) shows the same coil timing; on a Pro every ramp flasher pulse
  also pulses its lower flasher (19 with 22, 25 with 23; `tron/hw_numbers.py`), as the Pro's effects do.

`mpf game .` with no `-c` loads config.yaml alone, on MPF's default platform (smart_virtual), with an empty trough.
The unit tests and `tests/scenario.py` load config.yaml alone and force smart_virtual themselves
(`tests/tron_test.py`). `scripts/render_check.py` and `scripts/run.py` use the hw_virtual overlay by default.

## Desktop and MPF Monitor (hw_virtual)

```sh
python scripts/setup.py                    # once: installs MPF Monitor (mpf-monitor 1.0.0) into .venv too
python scripts/run.py --monitor            # Godot, then MPF (hw_virtual), then MPF Monitor; any OS
```

By hand (Linux/macOS paths; on Windows the venv's scripts are in `.venv\Scripts\`):

```sh
tools/godot/godot --path game &                              # GMC: MPF connects to it on port 5050
(cd game && ../.venv/bin/mpf game . -c config,hw_virtual)
(cd game && ../.venv/bin/mpf monitor)                        # MPF Monitor
```

MPF Monitor connects to MPF's own BCP server. MPF 0.80 always starts that server (`bcp: servers` in
mpf/mpfconfig.yaml: 127.0.0.1, port 5051, which is MPF Monitor's default port), so the overlay needs no BCP
setting. Do not pass `-b`, because it turns BCP off, and the monitor server with it. MPF also waits for
GMC on port 5050 (`bcp: connections: local_display`, required), so start Godot first.

`game/monitor/playfield.jpg` is a playfield picture rendered from the VPX table, and `monitor.yaml` places
every switch, lamp, flasher, coil, flipper, autofire and ball device of this config on it (the layout Vincent
supplied, renamed to these device names by SAM number and function). `settings.ini.default` holds MPF Monitor's
window positions; `run.py --monitor` copies it to `settings.ini` (git-ignored, MPF Monitor rewrites it) once. Click a spot to toggle a switch; drag a spot to move it and MPF Monitor saves it in
monitor.yaml. `scripts/gen_monitor.py` still draws the old labelled grid instead, but it overwrites this
layout: run it only to start over. `game/monitor/.gdignore` keeps Godot from importing the folder.

This was checked by booting `mpf game . -c config,hw_virtual -t` with Godot on Xvfb, with a BCP client on
port 5051 sending MPF Monitor's `switch?name=...&state=-1` toggles: three coins, then start. The log shows
`game_started` and `ball_started`, `c_trough_up_kicker` pulsing, `s_trough_1_r` going inactive and
`s_shooter_lane` going active. The client receives the switch device updates. `tests/test_hw_virtual.py`
checks the same thing, plus the trough shift: after the eject, switches 1-3 are active and switch 4 (L) is
not.

## The P-ROC machine (hw_proc)

### Files

| File | What it is |
|---|---|
| `game/config/hw_proc_le.yaml` | The LE overlay: platform, flippers, slingshots and pops as P-ROC hardware rules, flipper EOS switches, the DMD. It includes `rom/proc_numbers.yaml`. |
| `game/config/hw_proc.yaml` | The Pro overlay (the default): `hw_proc_le.yaml`, `machine_pro.yaml`, then `rom/proc_numbers_pro.yaml`. |
| `game/config/rom/proc_numbers.yaml`, `proc_numbers_pro.yaml` | Generated by `scripts/gen_config.py` from the SAM numbers in `rom/*.yaml` and `hardware.yaml` (and the Pro map). They hold the P-ROC number of every switch, coil and light. |
| `game/config/rom/coil_times.yaml` | Generated from `assets/rom_data/io/coils.csv`: the ROM's drive time for every coil. Included by `config.yaml`. |
| `game/tron/proc_hardware.py` | Ramp light tubes on the aux bus. Experimental and off by default (see "Ramp light tubes" below). |
| `game/tools/proc_dmd.gd` | Godot autoload. With `--proc-dmd` it sends the 128x32 DMD to MPF as 16-shade frames for the P-ROC. |
| `tests/test_proc.py` | Boots config + hw_proc_le (`tests/machine_proc_le.yaml`) and config + hw_proc (`tests/machine_proc.yaml`, Pro) against a mocked pinproc whose `decode()` is libpinproc's SAM decoder, and checks every address. |

### Running

You need libpinproc and pypinproc (github.com/preble) built for the machine's PC, and P-ROC firmware 2.14 or
newer (MPF warns about older versions). MPF 0.80.1's wheel carries pypinproc builds for Windows
(`mpf/platforms/pinproc/windows/pinproc.cp3xx-win_amd64.pyd`, Python 3.8-3.14) and macOS
(`mpf/platforms/pinproc/osx/pinproc.so`, an old Intel-only build); on Linux there is none.
`scripts/install/build_pinproc.sh` builds libpinproc and pypinproc and installs pypinproc into `.venv`
(`install_prereqs_linux.sh --proc` also installs the build packages and the udev rule; docs/requirements.md).
The P-ROC's FTDI USB driver must be installed on every OS.

```sh
python scripts/run.py --hw proc                         # any OS: Godot with --proc-dmd, then MPF with hw_proc
```

By hand:

```sh
.venv/bin/python scripts/gen_config.py                  # setup.py and the tests also run it
tools/godot/godot --path game -- --proc-dmd &           # GMC (the BCP server); --proc-dmd feeds the P-ROC DMD
(cd game && ../.venv/bin/mpf game . -c config,hw_proc)
```

To check the whole P-ROC config without a P-ROC, use `mpf game . -c config,hw_proc -x`. It runs every
device on the virtual platform.

Note: `driverboards: sternSAM` must go under `hardware:`, not under `p_roc:`. MPF validates
`p_roc: driverboards` as an enum and lowercases it to `sternsam`. pypinproc's `normalize_machine_type`
compares names with `strcmp` (pypinproc.cpp, `PyObjToMachineType`), so it would get an invalid machine type.

### Numbering (libpinproc `decode()`, machine type SternSAM)

| SAM | In the config | P-ROC number (libpinproc src/pinproc.cpp, PRDecode) |
|---|---|---|
| Matrix switch n (1-64) | `Snn` | `32 + 8*((n-1)/8) + 7-((n-1)%8)` when `(n-1)%16 < 8`, otherwise `32 + n-1` (range 32-95) |
| Dedicated switch #n (1-24) | `SD<n>` | `n + 7` (P-ROC direct inputs 8-31) |
| Coil/flasher n (1-32) | `Cnn` | `n + 31` (drivers 32-63, libpinproc's Stern coil groups 4-7) |
| Lamp n (1-80) | `Lnn` | `80 + 16*(7-((n-1)%8)) + (n-1)/8` (drivers 80-207, lamp matrix groups 10-25) |

The SAM numbers are the ROM's own. Matrix switches, coils and lamps come from the asset package. The
dedicated switches use SAM's dedicated switch numbering (PinMAME `src/wpc/sam.c`; the rules docs call the
slam tilt D-18), written `D<n>` in `hardware.yaml`.

| DED # | Function | MPF switch | P-ROC |
|---|---|---|---|
| 3 | Right coin slot (the one `tron/credits.py` counts) | `s_coin` | SD3 = 10 |
| 9 / 10 | Left flipper button / EOS | `s_left_flipper` / `s_left_flipper_eos` | 16 / 17 |
| 11 / 12 | Right flipper button / EOS | `s_right_flipper` / `s_right_flipper_eos` | 18 / 19 |
| 14 | Upper left flipper EOS | `s_upper_left_flipper_eos` | 21 |
| 17 | Tilt (plumb bob) | `s_plumb_bob_tilt` | 24 |
| 18 | Slam tilt | `s_slam_tilt` | 25 |
| 20 | Spare input: coin door open (see below) | `s_coin_door_open` | 27 |
| 21-24 | Coin door BACK, MINUS, PLUS, SELECT | `s_service_back/minus/plus/select` | 28-31 |

PinMAME's comment lists DED #22/#23 as Plus/Minus, but its input port, which is the code that actually runs,
has Minus on #22 and Plus on #23. The config follows the input port. Check the coin door buttons in switch test.

Coils: libpinproc sets every Stern driver group active high, so MPF reads polarity True from the P-ROC and
no `polarity` setting is needed. The ticket outputs 33-35 are latched from the aux bus and are not P-ROC
drivers. They stay on the virtual platform (the machine has no ticket dispenser).

### Coil settings (the ROM's, `rom/coil_times.yaml`)

The ROM's coil table and hardware rules are decoded (`assets/rom_data/io/coils.csv`, checked in the emulator),
so every coil uses the ROM's drive time on every platform. The Pro decompile shows the same timing
(`assets/rom_data/pro/README.md`); its lower flashers 22 / 23 get the ramp flashers' 48 ms.

- **Flippers** (coils 15, 16 and upper left 12) are single-wound: 40 ms full power, then 1 ms on / 11 ms off
  (`default_hold_power: 0.083`, a P-ROC patter). The upper flipper uses the left button. EOS switches are
  configured but not used (`use_eos: false`): the ROM's EOS cut is not modelled.
- **Slingshots and pops**: on SAM the CPU fired these in software. Here they are P-ROC hardware rules
  (`autofire_coils`), 32 ms (the ROM's bumper and sling rules; its recycle, 16 ms pops / 192 ms slings, is the
  P-ROC's own). The rules code still sees the switches and scores them. The package's `playfield_active` tag is
  removed from those five switches because the autofire device marks the playfield active itself, and MPF
  refuses the duplicate.
- **Kickers**: trough, auto launch and drop target reset 64 ms; VUK 64 ms at half power (the ROM's 1 ms on /
  1 ms off soft kick); knocker (optional coil 24) 80 ms; ticket meter 100 ms.
- **Orbit post** (coil 7): 64 ms, then 1 ms on / 6 ms off, cut after 4 s at most (`max_hold_duration`). The
  rules raise it for about 2 s.
- **Shaker** (coil 8): 200 / 384 / 1024 ms for strengths 1-3 (table 0x040d3998, the same on the Pro), gated by
  adjustment 86. A new run only replaces a shorter one.
- **Motors and relays** (5, 6, 8, 22, 23, 30): held on at 100 %.
- **Flashers**: the ROM's most common pulse for each (24-64 ms). The rules pass the ROM's own time when a call
  has one. A pulse longer than 255 ms (the P-ROC's pulse limit) becomes a timed enable.

### What changes from the original machine

- **CPU board**: removed. The IO board's CPU ribbon, the switch matrix and dedicated switch cables and the DMD
  ribbon go to the P-ROC's Stern connectors. Follow Multimorphic's P-ROC installation notes for Stern SAM
  for the connector mapping and the logic power feed. Leave the IO board, its power and the coin door
  high-voltage interlock as they are.
- **Sound**: the SAM sound system (DSP and amplifier) is on the CPU board, so it goes with the CPU. GMC
  plays the sounds on the PC. Feed a PC sound output through an amplifier to the original speakers.
- **DMD**: the P-ROC drives the original 128x32 DMD (MPF `dmds: dmd`, platform `p_roc`). GMC still draws
  the display. With `--proc-dmd`, `game/tools/proc_dmd.gd` sends each changed frame (up to 30 per second)
  to MPF as a 16-shade `dmd_frame`. This was checked end to end with Godot on Xvfb and
  `mpf game . -c config,hw_proc -x`: MPF's DMD device receives 4096-byte frames with shades 0-15. Without the
  flag, GMC can still show the display on an LCD. The P-ROC's DMD timing is libpinproc's default; set
  `p_roc: dmd_timing_cycles` if the shades look uneven.
- **GI**: the GI relay is bit 0 of the IO board's strobe latch (aux bus address 0xB). The P-ROC does not
  drive it as a driver. The bus capture in `assets/io/README.md` shows bit 0 low with GI on. A latch cleared
  at power-up should therefore leave GI lit, but this is not verified. The rules do not switch GI anyway.
- **Coin door open**: SAM reads the door from the IO board's interlock status register (20 V / 50 V
  present), which the P-ROC cannot read. `s_coin_door_open` is on DED #20, SAM's spare dedicated input. Wire
  a switch that closes while the door is open (for example a spare contact on the door interlock switch) to
  that input. Unwired, the door always reads closed. It shows the ROM's "50V / 20V DISABLED" warning (deff 4)
  and drives adj 41 (coin door ball saver) and adj 64 (tilt with the door open).
- **Ramp light tubes**: see below. Unless they are enabled, the fiber optic ramps stay dark.

### Ramp light tubes (experimental, off by default)

The two RGB fiber optic tubes are on the IO board's aux bus (`assets/io/README.md`). The ROM writes the
colour bit plane to AUX_DRV (address 6), then pulses the tube's strobe in the strobe latch (address 0xB):
left 0x10, right 0x20. It refreshes them with 4-bit binary-coded modulation, one plane per 250 us tick.

`tron/proc_hardware.py` turns that into a looping P-ROC aux port program. pypinproc already has the two
writes for SAM: `aux_command_output_primary` (enables 6, mux 1, which is AUX_DRV) and
`aux_command_output_secondary` (enables 11 = 0xB). The program writes data, strobe low and strobe high for
each tube, then waits 250, 500, 1000 or 2000 us for each plane. That is 28 commands, rewritten whenever
the 4-bit colour of `l_left_ramp_tube` / `l_right_ramp_tube` changes. The program keeps the latch at 0xFE
(bit 0 low, GI on), as the ROM does. `tests/test_proc.py` checks the command stream.

It is off until someone checks it on the machine, because a wrong address on this bus could write a coil
bank (addresses 0-3). To check it:
1. Coil power off (coin door open: the interlock cuts 50 V).
2. Set `machine_vars: proc_ramp_tubes: initial_value: 1` in `hw_proc_le.yaml` (on a Pro, also add `fiber_optics`).
3. With a logic analyzer on the IO board's CPU connector J1 (pinout in
   github.com/Ashram56/Stern-SAM-Databus-Analysis), confirm that the aux writes only hit addresses 6 and
   0xB, and that the data matches the colour.
4. Only then turn coil power back on.

Also confirm which tube is left and which is right. The ROM's console calls strobe 0x10 the left tube, but
PinMAME's comment says the opposite.

### First power-up (safety)

1. **No coil power at first.** Open the coin door (the interlock cuts the high voltage) or pull the
   solenoid fuses. Boot MPF and check that every driver stays off. libpinproc sets Stern drivers active
   high. A driver that turns on at boot means wrong polarity or wrong wiring: power off.
2. **Switch test** (service menu, `s_service_*`): close every switch and check its name. Check the trough
   (18-21), VUK (11), flipper buttons and EOS (DED 9-12), tilt, slam and the coin door buttons. If whole
   rows or columns are swapped, the cable is on the wrong P-ROC connector.
3. **Lamp test**: light each lamp alone and check it against `assets/io/lamps.csv`. Lamps 65 and 66 (start
   buttons) are on the two aux lamp strobes.
4. **Coils at low power**: before the first coil test, lower the coil's `default_pulse_ms` (for example
   10 ms) or set `default_pulse_power: 0.5`. pulse_power needs P-ROC firmware 2.14 or newer, as MPF
   points out (the VUK uses it). Fire each coil once, with a hand near the power switch, then raise it to the
   ROM's value (`rom/coil_times.yaml`). Check flippers last. Hold a flipper up for 30 s and feel the coil: the 1/12 hold
   should stay cool.
5. **Motors**: the disc and Recognizer motors run on relays (22, 23, 30) and on driver 5 or 6. Run them
   from the service menu with the playfield up and watch the position switches (52-56).
6. Leave the interlock wiring in place. libpinproc tickles the SAM IO board's watchdog. If MPF
   stops, the watchdog should drop every output: check this once by stopping MPF while a motor runs.

### Things to check on the real machine

- Coin door button order (DED #22 Minus / #23 Plus) and the coin slot (DED #3).
- Every coil time, especially the orbit post (does the 1/7 hold keep it up?), the VUK's half-power kick and
  the upper flipper.
- On a Pro: the T-R-O-N standup order (sw 1 = N), the disc direction relay on coil 3, and which lower flasher
  (22 / 23) sits on which side.
- The P-ROC's DMD shades and timing, and the startup frame. Godot's grey clear colour shows as shade 5
  until the first slide.
- GI comes on at power-up and stays on.
- The coin door switch on DED #20, if fitted.
- The ramp tubes, with the procedure above.

### Not mapped

- Ticket outputs (coils 33-35, aux bus): virtual only. The machine has no dispenser.
- GI on/off control: not driven (see above).
- IO board status inputs (zero cross, lamp driver status, interlocks): the P-ROC cannot read them.
- SAM's on-board sound: replaced by the PC (see above).
